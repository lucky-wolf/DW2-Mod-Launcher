# Mod catalog (browse and install mods outside Steam)

The launcher reads a public `index.json`, rebuilt daily by a GitHub Action in the catalog repository, and lists the mods in it. Players without Steam (Linux, other stores) can install and update from it, and authors can publish to it from the launcher. Design and decisions: DW2-XL `docs/ideas/Mod Release Catalog.md`. ## How it works today

- **Releases repo** `lucky-wolf/Distant-Worlds-2-Mods` (public; topics `dw2-mod`, `distant-worlds-2`, `mods`). A release is one per mod version: `<tag>.zip`, `<tag>.zip.sha256`, `<tag>.manifest.json`, and the preview `<tag>.preview.<png|jpg>`. Tag is `<Mod-name>-v<version>`. 18 releases exist: every published code mod and translation pack except XL. They were first made by DW2-XL's `scripts/release-mod.py`, since removed; the launcher's Publish makes the same files now (work item 2), releasing the folder at the moment it publishes.
- **Two separate steps for the owner:** the launcher's Publish dialog makes releases; DW2-XL's `python scripts/publish-catalog.py` only starts the catalog's workflow (`gh workflow run catalog.yml`) and waits for it (`gh run watch`; `--no-watch`). Neither runs the other. Re-releasing a changed tag deletes and recreates it, which resets its download count. `publish-catalog.py` warns about unpushed catalog changes (the workflow runs what is on GitHub).
- **Catalog repo** `lucky-wolf/Distant-Worlds-2-Mod-Catalog` (public). `build-index.py` + `.github/workflows/catalog.yml` run daily (05:17 UTC) and on demand, and commit `index.json` only when more than its timestamp changed. Discovery: every GitHub repo with the topic `dw2-mod`, plus `repos` in `pointers.json`, minus `blocked`. A release counts only if it has a `<tag>.manifest.json`; download counts and dates come from GitHub. GitLab projects are listed by hand in `pointers.json` (`gitlab`), the pointer carrying what a manifest would (`uid` and `author` required, `kinds` required, `tags`, `previewUrl`, `shortDescription`, `workshopId`, `dependencies`); GitLab has no public counts, so those are null. `pointers.json` also has `approved` (`{"<uid>": "owner/repo"}`, an owner's deliberate move of a mod to another repo).
- **One listing per `uid`**, from the repo that owns it (see item 1); within that repo the most recently published release wins. A GitLab zip is downloaded and hashed once per tag (the hash is carried over from the last index). The catalog repo's README tells authors about the `uid` and `author` requirement.
- **XL** is listed from GitLab (`coyote-wolf/DW2-XL`, `kinds: ["xml"]`, `previewUrl` into the XL repo, unversioned so a changed image shows stale from the launcher's cache) because it had no GitHub release when the catalog went live. Its `uid` (`363fba16-301d-41d4-979e-3432c10cbd59`) was written by hand into both `XL/dw2modlauncher.json` and the pointer so they agree. The old GitLab zip has no `uid` inside; installing it is accepted and matched by Workshop id. Once XL has a GitHub release (it now names `releaseRepo`, so the launcher can make one), that listing carries the same `uid` and the GitLab pointer can go.
- **The launcher's own Workshop item** (`DW2 Mod Launcher`) is a placeholder, not a mod: it exists on Steam for the page, description, change notes and a link to the real download. It is published from the launcher like any other item but names no `releaseRepo`, so GitHub starts unticked. Its GitHub release is the real launcher build, made by CI (`release.yml`) on every merge to `main`; `changelog.txt` feeds both the Steam change note and the release notes. It is not in the catalog (it cannot be installed as a mod); the launcher updates itself from GitHub's latest-release API. Deliberately not tied together.
- The launcher fetches `CatalogClient.DefaultUrl` (a raw GitHub address, no account). Nothing depends on a server of ours.

### index.json (schema 1)

`{ "schema": 1, "generated": "<utc>", "mods": [ ... ] }`, sorted by name. Each entry:

- `id` (a label, also the release file names), `uid` (**required**: the mod's identity, a lower-case hyphenated UUID, unique in the index), `name` (the mod's folder name), `version`, `author` (**required**), `shortDescription`, `workshopId` (number or null), `minLauncherVersion`, `dependencies` (`mod` required, `uid`, `workshopId`, `required`).
- `kinds`: non-empty, any of `code` (a .dll beside mod.json), `xml` (any .xml file), `translation` (a `language` in dw2modlauncher.json or a `translations/` folder), `font`. A mod may have several. Detected from the published files (`ReleasePackager.KindsOf`).
- `tags`: the author's topics from `tags` in dw2modlauncher.json, lower case, single spaces (`CatalogTags.Normalize`). May be empty.
- `size`, `sha256` (of the zip), `downloadUrl`, `releaseUrl`, `previewUrl` (null when none), `publishedAt`.
- `downloads` (total over all releases of the mod), `peakDownloads` (unused by the launcher now), `latestDownloads`; all null on GitLab.
- `repo`, `tag`, `zip`. Zips hold one root folder named like the mod with the published files, plus `dw2modlauncher.hooks.json` when present.

## Built in the launcher (788 tests pass)

[src/DW2ModLauncher.Core/Services/Catalog/](../../src/DW2ModLauncher.Core/Services/Catalog/); tests in `CatalogTests`, `CatalogBrowseTests`, `CatalogInstallerTests`, `CatalogDependenciesTests`, `CatalogClientTests`, `ReleaseTests`, `LauncherMetaTagsTests`.

- `CatalogParser`: strict schema 1 reader; a bad entry fails the read naming entry and field. An entry without `kinds`, `author` or a valid `uid` is rejected, as is a repeated `uid` and a dependency `uid` that is not a UUID.
- `CatalogStatusFinder`: the `uid` is the identity: an installed mod with the entry's `uid` (a Steam subscription means "from Steam", nothing to offer; a local one means up to date or update available), whatever it is called. A mod with a different `uid` is a different mod. Only installed mods with no `uid` yet are matched the old way (Workshop id; else same-named folder).
- `CatalogClient`, `CatalogTags` (normalization and the `Suggested` starting vocabulary), `CatalogPreviewCache` (previews cached under `<cache root>/Catalog/Previews/`, max 8 MiB, 4 at once).
- `CatalogInstaller` + the Download / Update button on each row (`CatalogViewModel.InstallAsync`): refuses while the game runs or when `minLauncherVersion` is above the launcher; confirms (source URL, size, author, and for a code mod that it runs on the player's machine); downloads to `<cache root>/Catalog/Downloads`, checks size and SHA-256; unpacks to a stage folder; copies into the mods folder. The new mod is first copied completely into a `.dw2ml-install-*` work folder beside the target (the mod scanner skips `.dw2ml-` folders); only then does an update send the old folder to the recycle bin and rename the work folder into its place, so any earlier failure leaves the installed copy untouched. The folder name is kept, so the mod stays enabled. Accepted zip layout: `mod.json` at the top, or exactly one root folder holding it. Entries with backslashes, absolute paths, `..` or `:` are refused; a fresh install never touches an existing folder of that name. **After an install or update the launcher stamps the entry's author into the mod's `dw2modlauncher.json` when the mod names none** (`LauncherMetaWriter.StampAuthor`, no overwrite).
- **Browse Mod Catalog window** (`CatalogDialog`, from the toolbar button at the right end of the Mods list; hidden when Settings turns the catalog off): fetches on open; search box; kind, tag and sort drop-downs; reload; one list whose rows show a 120x80 thumbnail, name, version, kinds, author, tags, description, install state, size, popularity, date; "Open release page". A failed fetch or bad entry is shown in the list area and logged (with a saved copy, the copy is shown under an orange notice); a missing or failed image is an empty slot, never another image. Keys are `Catalog*`, `PickTag*`, `PublishTag*`.
- **Sorts:** *Most downloads* (default; `downloads`, total over all releases ever, no figure last), *Most subscribers* (only offered once Steam has answered, then the default unless the player already chose; Steam's unique-subscriber count from the batched `QueryItems`, asked for entries with a Workshop id, no figure last), *Recently released*, *Name*. Each row shows subscribers when known, else downloads, labeled. Known skew: every update adds its own downloads, so a mod with many releases outscores one with few for the same players.
- **Tags for authors:** Edit Properties / Publish shows the tags as chips and a `+` opening `TagPickerDialog` (known tags = `CatalogTags.Suggested` + installed mods' tags + the loaded catalog's). Saved only when changed (`LauncherMetaWriter.SetTags`).
- **Mod right-click menu:** Configure, View Readme, Open Steam Page; Open Mod Folder, Code Hooks Report; Check Updates and Unsubscribe (Workshop mods only); Delete Mod (any local mod, the catalog's counterpart of Unsubscribe; still only enabled inside the managed mods folder); a **Mod Author** submenu (Edit Properties, Add translation, Rename, Make This a New Mod, Publish..., Mark Up to Date) for the player's *own* local mods only (`SelectedIsOwn`: author blank or equal to the Author setting). A catalog download by someone else shows no Author submenu.
- **Authorship rules:** Publish refuses when the Author setting is blank (`PublishNeedsAuthor`), so everything published carries an author; the setting defaults to the logged-in Steam account name.
- **Data locations:** settings, profiles, per-mod settings and `PublishedState` stay in the roaming `%AppData%\DW2ModLauncher` (`UserDataRoot.Get()`); anything that can be fetched again (the catalog's previews, downloads and saved index, the release work folder) goes in `UserDataRoot.GetCache()` (`%LocalAppData%\DW2ModLauncher`; `~/.local/share/DW2ModLauncher` on Linux; with `--data-root <folder>` the folder's `Cache` subfolder). Decided 2026-11-12 to keep `--data-root <folder>` as it is (no named "instances").
- Dialog title is "Browse Mod Catalog" (`CatalogTitle`); ja/ru/zh for changed keys are deleted for the release translation pass, new keys are English only.

## Work items

### 1. Mod identity (UUID): built

**Why.** Identity was the Workshop id, or for a mod without one its name; the catalog's `id` came from the tag text. A rename split one mod into two listings, mods by authors and players without Steam had no stable identity, and "newest release per `id` wins" let anyone tag a release with the same name and take over a listing.

**What exists.**
- `uid` in the mod's `dw2modlauncher.json` (never `mod.json`): a random UUID, written by `LauncherMetaWriter.StampUid` (`ModUid` canonicalizes). Read into `ModInfo.Uid`; one that is not a UUID reads as none.
- **Stamped only at the origin:** Create Mod (so a new mod has one from its first moment) and Publish (a mod made before identities existed gets its one at its first publish; a malformed one is reported and the publish stops). **Never by scanning**, and not in bulk for existing mods: stamping would make every published mod look modified. A downloaded mod keeps the `uid` it came with; one with none stays without.
- **Make This a New Mod** (Mod Author submenu): a fresh `uid` for a copy going its own way.
- **Duplicate detection** (`ConflictAnalyzer.AnalyzeEnabledCopies`) flags enabled copies by `uid`, then by Workshop id.
- **Catalog matching** by `uid` (see above). The release script and the launcher's packager both refuse a mod with no valid `uid` or no author. `build-index.py` rejects (stderr) any manifest or GitLab pointer without a valid `uid` and an author, keys listings on `uid`, and **pins each `uid` to the repo that owns it**: the repo in `pointers.json` `approved` (`{"<uid>": "owner/repo"}`), else the one the last index listed it from, else the one that released it first. Another repo's release of that `uid` is refused and reported; if the owner gave nothing this run, its last listing is kept.
- **Install check:** before anything in the mods folder is touched, the unpacked mod's own `uid` and `author`, when it states them, must match the catalog entry's (`CatalogInstaller.VerifyIdentity`); a mismatch or unreadable dw2modlauncher.json refuses the install and names both values. A mod that states neither (released before identities) is accepted and stays without a `uid`, matched by Workshop id.
- The Workshop id stays as an attribute (Steam operations, `PublishedState`, subscriber counts, the game's dependency resolution).
- **Dependencies by `uid`:** a `dw2modlauncher.json` dependency may carry `uid`; `ModDependencies.Find` matches it first (a mod with another uid is another mod; only a mod with no uid yet still matches by Workshop id or name). The catalog manifest and `CatalogDependency` carry it too.
- **Compatibility:** launcher 1.0.39 (no catalog, no `uid`) ignores the new keys (`System.Text.Json` skips unknown members); the game reads only `mod.json`. The catalog and its stricter index format are Unreleased, so no released launcher reads the index.
- **`LauncherMetaReader`:** `TryRead` reports an unreadable `dw2modlauncher.json`; the scan sets `ModInfo.LauncherJsonError`, shown with the scan problems and in the mod's details. `Read` logs it.

**Limits, stated plainly.** Pinning by repo stops casual takeover of a listed mod. It does not stop someone claiming a `uid` before its owner lists the mod (a `uid` is readable in any public zip), and it cannot tell a hostile move from a real one without the owner approving. Only a signature proves authorship; see item 5.

### 2. Publishing from the launcher: built

One Publish dialog sends a mod to Steam, GitHub, or both. It replaced DW2-XL's `release-mod.py` (removed).

- **No credentials in the launcher.** It shells out to `gh`, which uses the machine's login; if the tool is missing or not logged in it says so plainly with the install and login hint. GitHub only: the catalog lists GitLab only through hand-written pointers, so a GitLab release from the launcher would not make a mod listed (`glab` can follow if the catalog reads GitLab manifests).
- **The repository** is per mod: `dw2modlauncher.json` `"releaseRepo": "owner/name"` (`ModInfo.ReleaseRepo`, `LauncherMetaWriter.SetReleaseRepo`). It travels with forks and is where everyone agrees the mod is published. Edited in the Publish / Edit Properties dialog; the owner's 19 published mods already name `lucky-wolf/Distant-Worlds-2-Mods`.
- **Core (`Services/Publishing/`), a port of the old `release-mod.py`'s packaging:** `ReleasePackager` (tag, zip with the root folder and `dw2modlauncher.hooks.json`, `.sha256`, `.manifest.json`, preview chosen as `ModScanner` does, notes from the version's changelog section, `Differences` of a released zip against the folder; refuses a mod the catalog would reject, naming why; 2 GiB and 8 MiB limits), `GitHubReleaseHost` over `IProcessRunner` (`CheckReady`, `ReleaseExists`, `HasCatalogTopic`, `Create`, `Delete`, `DownloadZip`), and `ReleasePublisher` (the whole sequence). A test feeds the packager's manifest to `CatalogParser`. Differences from `release-mod.py`: a dependency's `required` is exactly what `dw2modlauncher.json` says (absent means false, as the launcher reads it), and a dependency without a `mod` name is refused, since the catalog parser requires one.
- **What is released:** the folder as it is at the moment of publish, minus what the Steam upload leaves out (`PublishedState.ContentFiles`).
- **The Publish dialog** (title *Publish*; menu item *Publish...*): a *Publish to* row with Steam Workshop and GitHub releases check boxes. The two Settings boxes (Mod authoring > *Publish to*) are **enablement only**: Steam Workshop (`PublishToSteam`, default on) makes the dialog offer Steam, ticked; GitHub releases (`PublishToGitHub`, default off) makes it offer the GitHub box and the repository field, and off hides both. Within a mod, GitHub starts ticked exactly when GitHub is enabled and the mod names a `releaseRepo`; either box can be changed for one publish. Nothing ticked, or GitHub ticked without a valid repository, disables Publish and says why. The Workshop id and visibility fields hide when Steam is unticked.
- **With Steam ticked,** `PublishAsync` runs as before, then releases on GitHub after the Steam upload, the changelog stamp and the state record. A GitHub failure never undoes the Steam publish: it is reported as "the Steam upload worked, but..." with gh's exact message, and publishing again with only GitHub ticked retries just that step.
- **With Steam unticked,** `PublishToGitHubOnlyAsync` skips every Steam check and upload: author and `uid` stamp, release, changelog stamp; the version is put back if the release does not happen.
- **Tag already exists:** same version, same files: nothing happens. Same version, changed files: the player is asked first, because replacing deletes the release and its tag and resets its download count (as the old `release-mod.py` did). The new release is fully built before the old one is deleted. A repository without the `dw2-mod` topic gets a warning: the catalog will not find its releases.
- **After:** `release-mod.py` is removed from DW2-XL; the launcher is the only way to release.

### 3. Dependencies and catalog settings: built

- **Dependencies.** `CatalogDependencies.Missing` finds what the player lacks (by `uid`, else Workshop id, else name). Download/Update with required mods missing offers a choice, never forced: *with required mods*, *only this mod*, or Cancel. The dialog names required mods the catalog lists (installed first through `CatalogViewModel.InstallOneAsync`; the first failure stops the rest), required ones it lacks ("get them elsewhere"), and optional ones (listed, not installed). A dependency that is installed but disabled counts as present; enabling is the launch check's job.
- **Settings.** Mod catalog section: *Show the Browse Mod Catalog button* (`CatalogEnabled`, default on; the catalog is contacted only when Browse opens) and *Catalog address* (`CatalogUrl`, blank = `CatalogClient.DefaultUrl`, must be https). `CatalogClient.LoadAsync` saves each good fetch to `<cache root>/Catalog/index-<hash of address>.json`; when the fetch fails it shows that copy under an orange notice (date and reason), and with no copy it reports the failure.

### 4. Steam as an option (a launcher that works fully without Steam): decided, planned, not started

**Why.** The launcher was built for Steam players: it finds the game through Steam libraries, expects a Workshop folder, asks Steam about subscriptions and updates at startup, and takes the default Author from the Steam account. A player on another store, or an author who publishes only to GitHub, would hit errors or blank fields. The owner decided (2026-11-12) that Steam is an *enablement*, like GitHub: an author or player uses Steam, GitHub, or both, and the launcher must cope with each.

**What the owner said.** The Settings boxes are enablement only (done for publishing, item 2). Within a mod, GitHub is used only when the mod names a repository; Steam only when Steam is enabled. Steam enablement is the part still to do, app-wide.

**Where Steam is assumed today (found 2026-11-12, to be gated):**
- `LauncherSettingsStore.Validate` returns `WorkshopFolderMissing` when a Workshop folder is set and absent; Settings cannot be saved without one.
- `SteamLocator` finds the game folder (`FindGameRoot`) and the Workshop folder (`FindWorkshopRoot`) through Steam libraries and the registry; `PathDetector` and the first-run flow assume it.
- Startup and Refresh call `RefreshSteamStatusAsync` (deleted-item and visibility checks through `ModPublisherFactory`), and `WorkshopUpdateService` checks Workshop updates.
- Browse's *Most subscribers* sort and per-row subscriber counts (`CatalogViewModel.LoadSubscribersAsync`).
- Mod menu items: Open Steam Page, Check Updates, Unsubscribe; the details panel's Steam links; the Settings *Steam helper process* option.
- The Author setting defaults to the logged-in Steam account name (`SteamLoginUser`).
- `GameLauncher` starts the game with `steam -applaunch` on Linux (Proton); Windows runs the exe directly.

**Design to carry out** (refined 2026-11-12 after reading the call sites):

1. **One switch, tri-state.** `LauncherSettings.PublishToSteam` (bool, default true, unreleased) becomes `SteamEnabled` (`bool?`): null = never decided. Settings label: *Use Steam* (a Steam section; the *Publish to* group keeps only GitHub). Null resolves once, at first run, to "Steam was detected" (a Steam install found by `SteamLocator.FindSteamRoots`), then is stored as a real bool. A player who turns it on with no Steam found gets a visible warning, not a refusal (user choices are law).
2. **Gate in one place, fail loudly.** `ModPublisherFactory` gets a static `Enabled` (set from settings like `UseHelperProcess`); `Create` throws `InvalidOperationException("Steam is turned off")` when off. 3. **Off means:**

Browse: no *Most subscribers* sort, downloads shown; default sort already downloads.
   - `LauncherSettingsStore.Validate` skips `WorkshopFolderMissing` (the folder is neither required nor checked). `PathDetector.Detect` no longer looks for a Workshop folder.
   - Author starts blank (null stays null; `PublishNeedsAuthor` already names the setting).
4. **Finding the game without Steam** (the part the owner stressed). Split `SteamLocator`: `IsGameRoot` moves to a neutral `GameFolder` class (it only checks for `DistantWorlds2.exe`); `SteamLocator` keeps libraries/Workshop/AppId. New `GameLocator.Find(currentRoot)` (built): the saved folder if valid, else Steam libraries, else GOG, else a direct purchase from Matrix (a standard Windows installer: `UninstallLocator` reads the "Distant Worlds 2" entry in the Windows uninstall list, taking `InstallLocation`, else the folder of `UninstallString` or `DisplayIcon`; the real entry's exact fields are unverified until someone reads one off a Matrix install), else nothing. Nothing found: the game-folder row in Settings shows a plain "not set" state and the main window shows a notice with a **Choose game folder...** button (no error dialog loop); picking validates with `IsGameRoot` and names exactly what is missing (`DistantWorlds2.exe`).
5. **First run:** detect Steam and the game; Steam on only when Steam exists. No game found: one notice (not an error) explaining that DW2 was not found and asking for the folder, with the Steam switch left as detected. The launcher stays fully usable for browsing the catalog and editing settings before a game folder exists; Play and mod install say what is missing.
6. **Workshop mods with Steam off (decided by the owner 2026-11-12: "they don't exist as far as we're concerned").** **Ignored entirely** (the saved Workshop folder is kept in settings, not scanned, not validated, so turning Steam back on restores it). Simplest and consistent with "off means no Steam"; a player who wants those mods copies them or leaves Steam on. Check `MissingModReferences` keeps `steam/<id>` entries in `mods.json` and profiles while the Workshop folder is unconfigured (its guard says it does when the folder "cannot be found"; add a test, since silently deleting a player's Workshop entries on toggle would be a real loss).

Few players, and the game is Windows-only so they would need their own Wine/Proton setup. ### 4b. Publish dialog layout (proposed 2026-11-12, owner deliberating; not built)

**Problems.** "Publish to" sits at the top of the scrolling area, far from the Publish button it decides. Workshop id and visibility take the second row though they mean nothing without Steam. The mod's `uid` is shown nowhere. The GitHub repository field is last in the scroll area, away from the GitHub box that needs it.

**Proposal.**
- **Scrolling area, top to bottom:** Title; Short description; Tags; one row of *Unique ID* (read-only, selectable, with a copy button; "assigned when you first publish" for a mod with none, since Publish stamps it) and *Preview image*; the Steam row (*Workshop ID*, *Visibility*) only when Steam is enabled and ticked for this publish; the Version row (version and steppers, version on publish, last published); then the existing expanders (description, bundles, injected DLLs, compatible with, change notes, status).
- **Fixed strip in the footer, above the buttons, outside the `ScrollViewer`:** `Publish to: [ ] Steam Workshop  [ ] GitHub releases  owner/name`. The repository box sits on this line and shows only while GitHub is ticked, so the strip keeps one line (the blocked-reason and invalid-repo messages go under it, orange as now). Rationale for the repository here rather than beside the Unique ID: it is part of *where* this publish goes, so it belongs with the boxes that choose that; the id is identity, not destination.
- **Edit Properties** has no targets, so the strip shows only the repository box (when GitHub is enabled in Settings).
- **Steam off:** no Steam box, no Steam row, no description push/pull buttons (the last two are already hidden), so the strip holds GitHub alone.
- **Avalonia:** the dialog is already `RowDefinitions="*,Auto"` (scroll area, footer); the strip is one more `Auto` row between them, so no new mechanism. A fixed 900-px window loses about 40 px of scroll area to it.
- **Build:** move the targets block and the repository box into the new row (same bindings: `ToSteam`, `ToGitHub`, `ReleaseRepo`, `PublishBlockedReason`); add `Uid`/`UidText` to `PublishDialogViewModel` from `ModInfo.Uid` with a copy command and English-only keys `PublishUniqueId`, `PublishUniqueIdNone`, `PublishCopyUniqueId`; reorder the grid rows. Check the build for `AVLN2000`.

### 5. Signing (design, not built)

The proper answer to impersonation (agreed 2026-11-12 that repo pinning is only a partial guard). On an author's first publish the launcher makes a keypair and keeps the private half in the user data folder (ECDSA P-256: in .NET's BCL, and verifiable in the Action with a pip package). The manifest carries the public key and a signature over `uid`, version and zip hash. The catalog pins `uid` to the key on first sight and accepts only releases signed by it; a key change needs the owner's approval in `pointers.json`. The launcher can check the same pin before installing, which also covers a compromised catalog. Cost: an author who loses the key cannot update without an approval, so the key needs a backup story (export/import in Settings).

## Gotchas learned

- After any `.axaml` edit run `dotnet build src/DW2ModLauncher.Avalonia/DW2ModLauncher.Avalonia.csproj -c Release --no-incremental` and read the output for `AVLN2000`. A XAML compile error leaves a DLL with no compiled XAML, the launcher then dies at startup with "No precompiled XAML found for App", and later incremental builds say "0 errors". `ListBox` has no `HorizontalContentAlignment` (style `ListBoxItem` instead).
- While the owner's launcher is open it locks the DLLs and `build.py` cannot finish: compile into a scratch folder inside the repo (`-p:OutDir=$PWD/temp/scratch-out/`; some tests find the source tree from the output path, so a folder elsewhere fails them) to check code and run `dotnet test`, never close their launcher.
- A JSON language file edited by a script: a raw line break inside a string breaks every pack at once (`LanguagePackTests`); write `\n` as the two characters.
- `PublishDialogViewModel` is built in two places in `MainViewModel` (Publish and Edit Properties); a new constructor argument must reach both.
- When the owner says they must do something first, it has not happened yet.
